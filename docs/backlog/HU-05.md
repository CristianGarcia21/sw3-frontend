# HU-05 · Cambiar el estado del caso

**Como** agente, **quiero** cambiar el estado del caso, **para** reflejar cómo avanza su atención.

| Campo | Valor |
|---|---|
| Tipo de caso relacionado | Incidente y Solicitud de servicio |
| Área / Categoría | Todas |
| Prioridad | P1 |
| Story Points | 5 |
| Sprint | 1 |
| Dependencias | HU-01 |

## Reglas de negocio
RN-08, RN-09, RN-10, RN-11, RN-13, RN-17.

1. Solo se permiten las transiciones de la tabla de `docs/02-requisitos.md`: Pendiente → En análisis → En atención → En validación.
2. `Cerrada` no se alcanza por aquí; solo por aprobación (HU-07).
3. Un caso `Cerrada` no cambia más.
4. Cada cambio crea un evento `CAMBIO_ESTADO` con estado anterior, estado nuevo, usuario y fecha.
5. En `Pendiente` o `En análisis` el agente puede corregir tipo, categoría y prioridad (clasificar y priorizar). Queda en historial como `RECLASIFICACION`.
6. En Sprint 1 se implementa la máquina de estados completa. La condición "tiene agente" (RN-11) se activa cuando se termine HU-04, y "tiene solución" (RN-13) con HU-06.

## Criterios de aceptación
- **Escenario 1: transición válida.** Given un caso `Pendiente`, When el agente lo pasa a `En análisis`, Then el estado cambia y se crea un evento en el historial.
- **Escenario 2: transición inválida.** Given un caso `Pendiente`, When se intenta pasar directo a `En validación` o `Cerrada`, Then el sistema responde error y el estado no cambia.
- **Escenario 3: caso cerrado.** Given un caso `Cerrada`, When se intenta cambiar su estado, Then el sistema lo impide.
- **Escenario 4: reclasificar.** Given un caso `En análisis` de prioridad P3, When el agente lo cambia a P1, Then se guarda la nueva prioridad y queda el evento en el historial.
- **Escenario 5: la interfaz guía.** Given el detalle de un caso, When el agente abre las acciones, Then solo ve los botones de las transiciones permitidas desde el estado actual.
